# Лабораторная работа №2, операционные системы - многопоточное умножение матриц

## Открытие проекта
1. Распакуйте ZIP.
2. Откройте папку проекта в IntelliJ IDEA как Maven-проект.
3. Убедитесь, что Project SDK и Maven Runner используют JDK 26 (в "pom.xml" задан release 26).
4. Нажмите Maven - Reload All Projects.
5. Запустите "src/main/java/org/example/Main.java" для демонстрационного запуска.
6. Запустите тесты из "src/test/java" или Maven Lifecycle - "test".

## Режим длительных измерений
В IntelliJ откройте Run - Edit Configurations - Main и добавьте в Program arguments:
"--bench"
Либо запустите из терминала после компиляции: 
"java -cp target/classes org.example.Main --bench"
Результаты CSV сохраняются в "results/":
- "dense.csv" - плотное умножение, время, ускорение и эффективность;
- "triangular.csv" - статическое/динамическое распределение;
- "power.csv" - возведение в степень с барьером;
- "ipc.csv" - генерация и передача по TCP.
Измерения намеренно не подставлены заранее: их нужно выполнить на целевом 
компьютере. Для плотных матриц заданы 500, 1000, 2000. Если последовательное 
умножение 2000×2000 занимает меньше 10–20 секунд, увеличьте последний размер 
в "BenchmarkRunner.SIZES". В "power.csv" используется n=700, p=3; если 
последовательное время меньше 10 секунд, увеличьте "n" в "runPower()".

## Важные пояснения
- Время обычного умножения не включает генерацию матриц: массивы создаются до старта таймера.
- Для каждого сочетания размера и числа потоков выполняются 5 измерений; минимальное и максимальное значения отбрасываются, усредняются оставшиеся 3.
- Порядок циклов "i-j-k" сравнивается с "i-k-j"; второй вариант обычно лучше использует последовательный доступ к строкам B и C.
- "MatrixPowerMultiplier" переиспользует рабочие потоки на всех шагах и синхронизирует их через "CyclicBarrier". Прогресс считает обработанные строки по всему объёму "(p-1)*n".
- Если убрать барьер, поток может начать следующий шаг до завершения предыдущего другими потоками. Тогда чтение/запись буферов пересекается, и результат становится гонкой данных: возможны неполные, устаревшие и недетерминированные значения. Не использовать такой вариант для получения корректного результата.
- IPC - TCP loopback, двоичный формат: сначала размеры (int), затем элементы (long). Измерение включает запуск JVM-процесса, генерацию и полную передачу, а не только чистое время сети. На серверном сокете есть тайм-аут подключения.
- "long" может переполниться при больших значениях и степенях. Для лабораторной используются небольшие случайные значения; при интерпретации больших экспериментов учитывайте ограничение "long".

## Сравнение IPC для отчёта
|Механизм | Скорость/накладные расходы | Сложность | Синхронизация | Между компьютерами | Переносимость |
|---|---|---|---|---|---|
| TCP-сокеты | Хорошая для больших блоков; есть копирование и протокольные расходы | Средняя | Потоки/протокол приложения | Да | Высокая |
| UDP-сокеты | Низкие накладные расходы, но нет гарантии порядка | Средняя | Нужно реализовать подтверждения и сборку | Да | Высокая |
| Каналы/именованные каналы (FIFO) | Обычно эффективны локально | Низкая–средняя | Потоковая передача, EOF | Обычно нет (локально) | Зависит от ОС |
| Общая память | Очень высокая для больших объёмов, минимум копирований | Высокая | Нужны mutex/semaphore | Нет, общая память одной машины | Ниже, зависит от ОС/API |
| Файлы | Обычно медленнее из-за файловой системы и диска/кэша | Низкая | Блокировки/атомарная публикация/EOF | Через общую ФС, не напрямую | Очень высокая |
| Очереди сообщений | Удобная доставка сообщениями, есть расходы ядра | Средняя–высокая | Часто встроенная | Зависит от брокера | Зависит от реализации |
TCP выбран потому, что он надёжен, сохраняет порядок байтов, поддерживает передачу между компьютерами и доступен стандартными средствами Java.

### Демонстрация отсутствия барьера
В "MatrixPowerMultiplier" добавлен метод "powerWithoutBarrier(int exponent)".
Он намеренно не синхронизирует потоки между шагами умножения. Запустить можно
из тестового/временного кода:
```java
long[][] result = new MatrixPowerMultiplier(matrix, 4)
        .powerWithoutBarrier(3);
```
Это демонстрационный ошибочный алгоритм: поток может начать следующий шаг
и переключить общие буферы, пока другой поток ещё читает предыдущий шаг.
Возникает гонка данных, поэтому результат недетерминирован и может отличаться
от последовательного. Даже если на конкретном запуске результат совпал,
это не доказывает корректность: ошибка зависит от планирования потоков.
Рабочий метод "power()" использует "CyclicBarrier" и остаётся правильным.
